This guide covers authentication methods for deploying to Google Cloud Platform, including local development and CI/CD workflows.

## Overview

There are three main authentication methods:

| Method | Use Case | Security | Recommended |
|--------|----------|----------|-------------|
| **gcloud CLI** | Local development | High | ✅ Yes |
| **Service Account Keys** | CI/CD (legacy) | Medium | ⚠️ Avoid |
| **Workload Identity Federation** | GitHub Actions | High | ✅ Yes |

## gcloud CLI Authentication (Recommended)

### For Local Development

This is the **recommended approach** for local Terraform deployments.

::steps

### 1. Install gcloud CLI

```bash [Terminal]
# macOS
brew install google-cloud-sdk

# Or download from https://cloud.google.com/sdk/docs/install
```

### 2. Authenticate Your User Account

```bash [Terminal]
# Login with your Google account
gcloud auth login

# This opens a browser window for OAuth authentication
# After login, your credentials are stored locally
```

### 3. Set Application Default Credentials

```bash [Terminal]
# This allows Terraform to use your credentials
gcloud auth application-default login

# Stores credentials at:
# ~/.config/gcloud/application_default_credentials.json
```

### 4. Set Your Project

```bash [Terminal]
# Set the active project
gcloud config set project YOUR_GCP_PROJECT_ID

# Verify
gcloud config get-value project
```

### 5. Verify Authentication

```bash [Terminal]
# List authenticated accounts
gcloud auth list

# Should show your email with * (active)
# Example output:
#        Credentialed Accounts
# ACTIVE  ACCOUNT
# *       you@example.com
```

::

## Avoiding Common Issues

### Don't Mix Authentication Methods

::prose-warning
**Critical**: Unset `GOOGLE_APPLICATION_CREDENTIALS` when using gcloud CLI auth.
::

If you have service account keys set via environment variables, they will **override** gcloud CLI authentication and cause permission errors.

```bash [Terminal]
# Check for conflicting credentials
env | grep GOOGLE

# If GOOGLE_APPLICATION_CREDENTIALS is set, unset it:
unset GOOGLE_APPLICATION_CREDENTIALS

# Verify it's gone
env | grep GOOGLE
```

### Why This Matters

When `GOOGLE_APPLICATION_CREDENTIALS` is set:
- Terraform uses the service account key file
- gcloud CLI auth is ignored
- You may get "Permission Denied" errors if the service account lacks permissions

**Solution**: Use gcloud CLI auth for local development, not service account keys.

## Service Account Keys (Not Recommended for Local)

Service account keys should **only** be used when gcloud CLI isn't available (e.g., non-interactive environments).

::prose-warning
Service account keys are long-lived credentials that pose a security risk if exposed. Prefer gcloud CLI or Workload Identity Federation.
::

### Creating a Service Account Key

If you must use a service account:

```bash [Terminal]
# Create service account
gcloud iam service-accounts create terraform-deploy \
  --display-name="Terraform Deployment"

# Grant necessary roles
gcloud projects add-iam-policy-binding YOUR_GCP_PROJECT_ID \
  --member="serviceAccount:terraform-deploy@YOUR_GCP_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/editor"

# Download key (keep this secure!)
gcloud iam service-accounts keys create ~/gcloud-key.json \
  --iam-account=terraform-deploy@YOUR_GCP_PROJECT_ID.iam.gserviceaccount.com
```

### Using the Key

```bash [Terminal]
# Set environment variable
export GOOGLE_APPLICATION_CREDENTIALS="$HOME/gcloud-key.json"

# Terraform will now use this service account
terraform plan
```

### Security Best Practices

- ✅ Store keys in secure credential managers (1Password, Vault)
- ✅ Use minimal IAM roles (principle of least privilege)
- ✅ Rotate keys regularly (every 90 days)
- ✅ Delete keys when no longer needed
- ❌ Never commit keys to git
- ❌ Never share keys in chat/email
- ❌ Don't use long-lived keys for local development

## Workload Identity Federation (GitHub Actions)

This is the **most secure** method for CI/CD - no keys required!

### How It Works

Workload Identity Federation uses **OpenID Connect (OIDC)** to exchange short-lived tokens between GitHub and Google Cloud, eliminating the need for service account keys.

#### Authentication Flow

```
┌─────────────────┐
│  GitHub Actions │
│    Workflow     │
└────────┬────────┘
         │ 1. Request OIDC token
         ▼
┌─────────────────┐
│     GitHub      │  Token contains:
│  OIDC Provider  │  - repository: "owner/repo"
└────────┬────────┘  - ref: "refs/heads/main"
         │            - actor: "username"
         │ 2. Issue signed JWT token
         ▼
┌─────────────────┐
│ Google Cloud    │
│ Workload        │  3. Validate token:
│ Identity Pool   │  - Verify signature
└────────┬────────┘  - Check repository_owner
         │            - Verify issuer (GitHub)
         │ 4. Exchange for GCP credentials
         ▼
┌─────────────────┐
│   GCP Service   │  5. Return temporary credentials
│    Account      │     (valid ~1 hour)
└─────────────────┘
```

#### Step-by-Step Process

1. **GitHub generates OIDC token** (when workflow runs with `id-token: write` permission)
   - Token is a signed JWT containing workflow metadata
   - Includes repository, ref, actor, and other claims
   - Valid for ~10 minutes

2. **Google Cloud validates token**
   - Verifies signature using GitHub's public keys
   - Checks `repository_owner` matches Terraform's `attribute_condition`
   - Confirms issuer is `https://token.actions.githubusercontent.com`

3. **Token exchange for credentials**
   - If valid, GCP issues temporary service account credentials
   - Credentials last ~1 hour (automatically refreshed by GitHub Actions)
   - Scoped to permissions of `github-actions-deploy` service account

4. **Workflow uses credentials**
   - Push Docker images to Artifact Registry
   - Deploy to Cloud Run
   - Read secrets from Secret Manager

5. **Automatic cleanup**
   - Credentials expire after workflow completes
   - No manual revocation needed
   - Next workflow run gets fresh credentials

#### What Makes This Secure?

**No Long-Lived Secrets**:
- ✅ No service account keys stored in GitHub
- ✅ Tokens expire automatically
- ✅ Can't be accidentally committed to git
- ✅ Can't be leaked in logs (GitHub masks them)

**Repository Scoping**:
- ✅ Tokens only valid for specific repository
- ✅ Can't be reused in other projects
- ✅ Terraform enforces `repository_owner` check

**Automatic Rotation**:
- ✅ New token for every workflow run
- ✅ No manual key rotation needed
- ✅ No key expiration to worry about

**Audit Trail**:
- ✅ Every token exchange logged in GCP
- ✅ GitHub Actions logs show which workflows ran
- ✅ Cloud Run revisions show who deployed

#### Comparison: Workload Identity vs Service Account Keys

| Feature | Workload Identity | Service Account Keys |
|---------|-------------------|---------------------|
| **Lifetime** | ~1 hour (auto-renewed) | Forever (until revoked) |
| **Storage** | None (generated per-run) | Stored in GitHub Secrets |
| **Rotation** | Automatic | Manual |
| **Leak Risk** | Very low (short-lived) | High (long-lived) |
| **Revocation** | Automatic on expiry | Manual deletion required |
| **Setup** | Terraform creates WIF pool | Create & download JSON key |
| **Best For** | CI/CD, automated workflows | Legacy systems, local dev |

#### Why Use Workload Identity?

**Google's Recommendation**: Workload Identity is the **official recommended approach** for external workloads (like GitHub Actions) to authenticate to GCP.

**Industry Standard**: OIDC token exchange is used by:
- AWS (OIDC for GitHub Actions)
- Azure (Federated Identity Credentials)
- HashiCorp Vault (JWT/OIDC auth)

**Benefits**:
- ✅ No credentials to manage
- ✅ Automatic token rotation
- ✅ Scoped to specific repositories
- ✅ Can't be accidentally leaked
- ✅ Meets compliance requirements (no static keys)

### Setup (Automated by Terraform)

Our Terraform configuration automatically creates:
- Workload Identity Pool (`github-actions-pool`)
- Workload Identity Provider (`github-provider`)
- Service account with minimal permissions (`github-actions-deploy`)

```hcl [infra/terraform/main.tf]
resource "google_iam_workload_identity_pool" "github" {
  workload_identity_pool_id = "github-actions-pool"
  display_name              = "GitHub Actions Pool"
}

resource "google_iam_workload_identity_pool_provider" "github" {
  workload_identity_pool_id = google_iam_workload_identity_pool.github.workload_identity_pool_id
  workload_identity_pool_provider_id = "github-provider"

  attribute_condition = "assertion.repository_owner == 'YOUR_GITHUB_USERNAME'"

  oidc {
    issuer_uri = "https://token.actions.githubusercontent.com"
  }
}
```

### GitHub Secrets Required

After running `terraform apply`, add these secrets to your GitHub repository:

```bash [Terminal]
# Get values from Terraform outputs
cd infra/terraform

terraform output workload_identity_provider
terraform output github_actions_service_account
```

Add to GitHub: `https://github.com/YOUR_USERNAME/YOUR_REPO/settings/secrets/actions`

| Secret | Value |
|--------|-------|
| `GCP_PROJECT_ID` | Your GCP project ID |
| `GCP_REGION` | e.g., `europe-west2` |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | Full provider path from terraform output |
| `GCP_SERVICE_ACCOUNT` | Service account email from terraform output |

### Using in GitHub Actions

```yaml [.github/workflows/deploy.yml]
jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write  # Required for OIDC

    steps:
      - uses: actions/checkout@v4

      - name: Authenticate to Google Cloud
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.GCP_WORKLOAD_IDENTITY_PROVIDER }}
          service_account: ${{ secrets.GCP_SERVICE_ACCOUNT }}

      - name: Deploy to Cloud Run
        run: |
          gcloud run deploy my-service \
            --image gcr.io/project/image:latest \
            --region ${{ secrets.GCP_REGION }}
```

## Troubleshooting

### "Permission Denied" Errors

**Check which authentication method is active:**

```bash [Terminal]
# Is GOOGLE_APPLICATION_CREDENTIALS set?
echo $GOOGLE_APPLICATION_CREDENTIALS

# Which gcloud account is active?
gcloud auth list

# Which credentials will Terraform use?
gcloud auth application-default print-access-token
```

**Common causes:**
1. Service account key via `GOOGLE_APPLICATION_CREDENTIALS` lacks permissions
2. Using wrong gcloud account (switch with `gcloud config set account`)
3. Application default credentials not set (`gcloud auth application-default login`)

### "Error 403: The caller does not have permission"

Your authenticated user/service account needs these roles:
- `roles/editor` (or more specific roles)
- `roles/iam.serviceAccountAdmin` (to create service accounts)
- `roles/resourcemanager.projectIamAdmin` (to manage IAM)

```bash [Terminal]
# Grant yourself the necessary roles
gcloud projects add-iam-policy-binding YOUR_GCP_PROJECT_ID \
  --member="user:you@example.com" \
  --role="roles/editor"
```

### "Application Default Credentials Not Found"

```bash [Terminal]
# Fix: Set application default credentials
gcloud auth application-default login

# Verify credentials exist
ls ~/.config/gcloud/application_default_credentials.json
```

### Switching Between Projects

```bash [Terminal]
# List all projects
gcloud projects list

# Switch project
gcloud config set project YOUR_GCP_PROJECT_ID

# Update application default credentials for new project
gcloud auth application-default login
```

- [ ] Installed gcloud CLI

- [ ] Ran `gcloud auth application-default login`
- [ ] Set correct project with `gcloud config set project`

- [ ] Verified active account with `gcloud auth list`
- [ ] User/service account has necessary IAM roles
